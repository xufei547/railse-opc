# 审批瓶颈已从"点按钮"移到"谁在等我"

**2026 年末，开发者同时跑 Claude Code / Codex CLI / Gemini CLI（现为 Antigravity CLI）时的痛点按出现频率排是：第一，提示疲劳与"always allow 不生效"（12+ 个独立来源，四家 CLI 都有）；第二，多会话时"不知道哪个 agent 在等我"、人离开后 agent 空等（10+ 来源）；第三，YOLO 太险、想要安全的自动放行（8+）；第四，在手机上批准或回答（7+）；第五，多 agent 协调（6+，几乎全是跑 8–30 个会话的重度用户）。** 官方在 2026 下半年把第三、四条大体收编：Claude Code 于 8 月 14 日把 auto mode 设为默认并有 Remote Control，OpenAI 于 10 月 6 日把 Codex Auto-review 免费并把手机远程控制 GA，Google 于 8 月 21 日给 Antigravity 上线 Remote Control。但三家都留下同样的四个结构缺口：没有跨 CLI 的统一收件箱、全部走厂商中继、Remote Control 明确排除 API key / 网关 / ZDR 用户、"记住这个决定"没有作用域选择。第三方生态里纯审批转发器普遍不到 100 star 且 2–4 个月停更，长大的都是"审批之外还多一点"的产品（herdr 47k、Happy 24k、cc-connect 16k），带规则引擎的只有收费的 Pushary 与封闭的 Greenlight。Railse v0.2.0 恰好站在四个缺口的交汇处（三 CLI 一个收件箱、自托管、确定性七档规则加硬底线、永不卡死的 fail-open），但也有明确短板：Codex 只在交互会话介入且模型约 8–10 分钟就放弃等待，Gemini 只能拒不能批而且 Gemini CLI 本身已被 Antigravity CLI 取代，没有任何统计或审计导出，"记住"学不了复合命令，推送队列在内存里。接下来几版最值得做的依次是：验证 auto mode 成默认后 Railse 的钩子链路是否照旧；把"记住"做成带作用域的精确规则；用 hub 已有数据做"省掉多少次打扰"的统计页；持久化推送队列并补齐 iOS 真机三项验证；补一个 deny-only 的 Antigravity 适配并把 Gemini 标为 legacy。明确不该做的是：自研分类器、终端复用/PTY、聊天桥、团队二审、托管中继。

## 痛点排序：提示疲劳第一，"谁在等我"第二，两者在重度用户身上合流

提示疲劳是所有 CLI 用户口径最一致的抱怨。Claude Code issue #11380 拿到 64 个赞、被 bot 关闭锁定且没有维护者回复，里面的话是 **"This is the single largest flaw in Claude Code"** 和 "Having to babysit permission prompts defeats the purpose of having an AI assistant"（[GitHub #11380](https://github.com/anthropics/claude-code/issues/11380)）。HN 上 auto mode 成默认那条 292 分、313 评论的帖子里，最被引用的是 "I just cannot approve seven trillion approval prompts and stay sane" 和 "I'm not even reading the commands"（[HN 49239021](https://news.ycombinator.com/item?id=49239021)）。Anthropic 自己的遥测给了量化底座：**用户批准了约 93% 的提示**，Anthropic 把它直接归因为审批疲劳（[Anthropic, How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)）；HN 上流传的是 97%，出自公告转述（[HN 49239021](https://news.ycombinator.com/item?id=49239021)）。Simon Willison 2 月的 X 投票里 **41.2% 的人"通常"直接跑 `--yolo` / `--dangerously-skip-permissions`**，其中 44% 没有沙箱（[Simon Willison on X](https://x.com/simonw/status/2022323970276786460)，二手转述）。"Continue? Y/N" 这个小游戏累计 409k 次决策，玩家整体只有 66.3% 准确率，`npm run analyze` 这类威胁被 64.7% 的人放行，7% 的人什么都批（[scalex.dev](https://scalex.dev/blog/ai-agent-permissions-stats/)）。疲劳的根子不是提示多，而是 **"我已经 allow 过了它还在问"**：issue #34106 里 `BRANCH=$(git branch --show-current) && …` 因为含 `$()` 不匹配 `Bash(git:*)`，`pnpm build 2>&1` 被标 "quoted characters in flag names"，一个跑 10 个无人值守实例的用户被卡 "4+ hours with no timeout"，同样被 bot 关闭无回复（[GitHub #34106](https://github.com/anthropics/claude-code/issues/34106)）。Codex 那边 #22181 的方向正好相反：按一次 "don't ask again for commands that start with curl" 会生成一条跨会话、跨工作区、永不过期的 `curl` 放行规则（[openai/codex #22181](https://github.com/openai/codex/issues/22181)）。Gemini CLI 的 YOLO 模式反复回归到"每隔几秒弹一次"（[#26414](https://github.com/google-gemini/gemini-cli/issues/26414)、[#29682](https://github.com/google-gemini/gemini-cli/issues/29682)）。

第二条痛点在单会话用户那里只是"没听到提示音"，在多会话用户那里变成了调度问题。Claude Code #36885 的原话是 **"The bottleneck increasingly isn't Claude's speed — it's the human noticing that Claude is waiting."**，同样被 bot 以 not planned 关闭（[GitHub #36885](https://github.com/anthropics/claude-code/issues/36885)）。Josh Morony 跑约 8 个 tmux 会话、20 个终端窗口，写道 "I would lose track of which of my projects currently had agents running"，并且"The more instances of Claude Code I was using the worse it would get."（[joshmorony.com](https://www.joshmorony.com/effectively-manage-attention-across-multiple-coding-agents/)）；Marcin Gadomski 同时开 10–20 个 Claude Code 加 Codex 加 OpenCode，总结为 "agents idling while they wait for a one-word answer" 与 "The second thing I lost was the overview."（[dev.to](https://dev.to/marcingadomski94/how-i-run-many-claude-code-agents-at-once-without-losing-track-60)）。一篇教程算过账：一个 20 分钟的任务 "spent eighteen of those minutes waiting for you to approve one permission"（[wmedia.es](https://wmedia.es/en/tips/claude-code-notifications-on-your-phone)）。Codex 在这条上最弱：外部 `notify` 钩子至今只在 `agent-turn-complete` 触发，等待审批时不发通知（[#11808](https://github.com/openai/codex/issues/11808)、[#19921](https://github.com/openai/codex/issues/19921)、[#17716](https://github.com/openai/codex/issues/17716)）。Gemini CLI 的声音通知请求拿了 74 个赞，最终被归并进泛化的 hooks 需求（[GitHub #4310](https://github.com/google-gemini/gemini-cli/issues/4310)）。三家 issue 追踪器呈现同一模式：**"告诉我哪个在等"被厂商当成 hooks 问题关掉，用户却把它当成产品问题**。

第三到第五条的分布说明了市场切片。想要"介于 YOLO 和保姆之间"的人贡献了 "agent mistakenly though $HOME was theirs and deleted it" 这类事故叙述，以及对 auto mode 分类器 "quite annoying and overly zealous, but probably pretty effective" 的评价（[HN 49239021](https://news.ycombinator.com/item?id=49239021)）；2026 年 4 月的 PocketOS 事件把这条痛点推上主流媒体：Cursor 上的 Opus 4.6 用九秒删掉生产数据库 "plus all of its backups"，没有请求确认，停机 30 小时以上（[Euronews](https://www.euronews.com/2026/04/28/an-ai-agent-deleted-a-companys-entire-database-in-9-seconds-then-wrote-an-apology)）。手机批准这一条的用户画像是 "activate /remote-control and approve from mobile while walking around"（[HN 49239021](https://news.ycombinator.com/item?id=49239021)），Gemini CLI 用户提的同类需求则被一天内以 "no immediate plans" 关闭（[GitHub #27289](https://github.com/google-gemini/gemini-cli/issues/27289)）。多 agent 协调的声音全来自 "running 30+ agents in parallel" 这一层（[HN 49239021](https://news.ycombinator.com/item?id=49239021)），而 Stack Overflow 5 月的 pulse survey 显示 **68% 的开发者更偏好单 agent 配置**（[Substack 转述](https://practicalaidatascience.substack.com/p/one-developer-multiple-agents-parallel)）。所以并行数是痛点类型的最强预测变量：单会话用户抱怨提示量，8 个以上会话的用户抱怨注意力路由；前者是大众市场，后者是小而响亮的工具活跃层。没有任何 2026 年的调查直接测过"你同时跑几个 agent"或"你每天等提示多久"，这是本报告频率排序的根本局限：计数是独立来源数，不是人群比例。

## 官方在 2026 下半年收编了手机批准与风险式放行，但留下四个结构缺口

三家官方的手机路径在架构上同构：本机进程出站长连接到厂商中继，再到厂商 Web 或 App。Claude Code Remote Control 的原文是 "makes outbound HTTPS requests only and never opens inbound ports"，代价是 **"the session transcript ... is stored on Anthropic servers"**，并且 "available on Pro, Max, Ultra, Team, and Enterprise plans. API keys are not supported."，ZDR/HIPAA 组织 "can't enable Remote Control"，Bedrock / Vertex / Foundry / 自建网关用户同样被排除（[Remote Control docs](https://code.claude.com/docs/en/remote-control)）。推送只有两个开关 "Push when Claude decides" 与 "Push when actions required"，"there is no per-event configuration"。它的早期可靠性记录不好看：权限提示不转发到手机（#36439）、手机批准后主机卡死（#52084）、iOS 推送静默无声或根本不到（#58851、#55786、#60208）（[claudeissues 52084](https://claudeissues.com/issue/52084-remote-control-approving-permission-from-phone-hangs-claude-code-on-host)、[claudeissues 58851](https://claudeissues.com/issue/58851-bug-remote-control-mobile-push-notifications-not-delivered-on-ios-despite-connec)、[GitHub #60208](https://github.com/anthropics/claude-code/issues/60208)）。Channels（Telegram / Discord / iMessage）给了第二条官方路径，并定义了 "permission relay capability"，但它仍是 research preview、只接受 Anthropic 维护的插件白名单、需要 Bun，而且文档直说 "Anyone who can reply through the channel can approve or deny tool use"（[Channels docs](https://code.claude.com/docs/en/channels)）。

Codex 走得更宽也更乱。手机远程控制 5 月以预览形式覆盖包括 Free 和 Go 在内的所有套餐，6 月 25 日 GA，主机通过 "outbound TLS connection to an OpenAI-maintained relay"，CLI 侧有实验性的 `codex remote-control start|stop|pair`（[aiweekly](https://aiweekly.co/alerts/openai-codex-remote-reaches-all-chatgpt-plans-with-mobile-access)、[codex.danielvaughan.com](https://codex.danielvaughan.com/2026/07/10/codex-remote-ga-qr-relay-architecture-mobile-approvals-ssh-host-cli-developer-guide/)）。风险式放行是 `approvals_reviewer = "auto_review"`：只审"本来就要审批"的动作，低中风险放行、critical 拒绝、high 交用户，失败 "fail closed"（[Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)），**10 月 6 日起对 ChatGPT 登录用户免费且不计入套餐**（[nerdschalk](https://nerdschalk.com/codex-auto-review-is-now-free-for-chatgpt-sign-ins/)）。用户抱怨集中在持久性与一致性："don't ask again" 不持久（[#14936](https://upd.dev/openai/codex/issues/14936)）、`approval_policy = "never"` 对 MCP 调用仍弹（[#13476](https://upd.dev/openai/codex/issues/13476)）、切目录后会话内 allow 失效（[aident.ai](https://aident.ai/blog/fix-codex-session-approval-repeats-after-cwd-change)）、PermissionRequest 钩子在 Auto-review 已处理时照样触发导致假"需要你"（[#28833](https://github.com/openai/codex/issues/28833)）、配置项频繁改名（`guardian_subagent` → `approvals_reviewer`，`--full-auto` 退役）（[Config reference](https://learn.chatgpt.com/docs/config-file/config-reference)）。对第三方最要紧的一条是 hooks 文档自己写的 "Treat tool hooks as a useful guardrail, not a complete enforcement boundary"，以及 `PreToolUse` 的 `"ask"` 至今 "parsed but not supported yet"（[Codex Hooks](https://learn.chatgpt.com/docs/hooks)）。

Gemini 这条赛道在 2026 年下半年应当改读为 Antigravity。Google 5 月 19 日宣布，6 月 18 日起 Gemini CLI "will stop serving requests" 对免费与 AI Pro/Ultra 个人用户，仅对付费 API key 用户保留，继任者 Antigravity CLI（`agy`）保留 Hooks 等能力但 "there won't be 1:1 feature parity"（[Google Developers Blog](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/)）。Gemini CLI 的 policy engine 文档停在 4 月，并承认工作区层策略 "will not have any effect"（[Policy engine](https://geminicli.com/docs/reference/policy-engine/)）。Antigravity 在 8 月 21 日上线 Remote Control，CLI 会话可从 Web 仪表盘响应工具确认与澄清问题，但 "You cannot change settings from the remote web interface"，套餐门槛与流量路径未说明（[Antigravity Remote Control docs](https://www.antigravity.google/docs/remote-control)、[Gigazine](https://gigazine.net/gsc_news/en/20260822-antigravity-remote-control/)）；其 `auto` 模式处于 Preview 且 "isn't available for business or enterprise accounts"（[Antigravity CLI modes](https://www.antigravity.google/docs/cli/modes)）。第三方来源称 agy 的钩子 "an allow result does NOT suppress agy's own request-review confirmation"（[safe-chains agy.rs](https://docs.rs/safe-chains/latest/src/safe_chains/targets/agy.rs.html)），这与 Railse 在 Gemini CLI 上观察到的"allow 不跳过原生框"是同一类限制。Stack Overflow 2026 的使用份额给出了权重：Claude Code 65.5%、Codex 29.5%、Cursor 25.5%、**Google Antigravity 16.0%**、Gemini Code Assist 14.6%（n=12,255）（[survey.stackoverflow.co](https://survey.stackoverflow.co/2026/ai/data/ai-code-agent)）。

把三家摆在一起，官方正在吃掉的是"单 CLI 的手机批准加推送"和"风险式自动放行"两块；尚未触及的是四块：跨 CLI 统一收件箱（三家文档均无）、不经厂商中继的自托管、被 Remote Control 明确排除的 API key / 网关 / ZDR / HIPAA 用户以及 Antigravity `auto` 不开放的企业账号、以及"记住这个决定"的作用域选择。还有一个被低估的变化：Claude Code 从 v2.1.283 起 "auto mode is the built-in starting mode for interactive terminal and VS Code sessions"，大部分提示由分类器消化，**永远会弹的只剩显式 ask 规则、`AskUserQuestion`、关键路径 `rm`** 这几类（[Permission modes](https://code.claude.com/docs/en/permission-modes)）。这意味着"Remote Control 什么都弹"的前提不再成立，手机审批的真实流量正在变少、变重。

## 第三方生态：纯审批转发器活不过一季，规则引擎是收费点

按 2026-11-01 的 GitHub 数据，这个赛道最大的两个仓库都不是审批产品：**herdr 47,211 star**（3 月创建，终端多路复用器，agent 通过 OSC 7501 报 working / done / waiting on you，不碰权限提示，没有手机端）与 **Happy 24,440 star**（全功能手机客户端，E2E 中继，1,093 个 open issue）（[herdr.dev/docs/remote](https://herdr.dev/docs/remote)、[slopus/happy](https://github.com/slopus/happy)）。cc-connect 以 **16,189 star、1,694 fork、629 个 open issue** 代表"把整个 agent 搬进飞书/Telegram"的聊天桥路线，卖点是出站 WebSocket "no public IP required for most platforms"，审批只有 `/mode yolo` 与 `/mode default` 两档（[chenhg5/cc-connect](https://github.com/chenhg5/cc-connect)）。专做审批的工具天花板低得多：Remodex 3,348 star 但只支持 Codex/OpenCode 且作者自称 "Expect bugs."，上次推送 10 月 1 日（[Emanuele-web04/remodex](https://github.com/Emanuele-web04/remodex)）；CC Pocket 1,094 star，LAN/Tailscale 桥接，"The Bridge goes offline while a Mac sleeps"（[K9i-0/ccpocket](https://github.com/K9i-0/ccpocket)）；ductor 464 star 但 7 月 23 日后停更、60 个 open issue（[PleasePrompto/ductor](https://github.com/PleasePrompto/ductor)）；claude-threads 46 star、anotifier 35 star 虽活跃但很小（[anneschuth/claude-threads](https://github.com/anneschuth/claude-threads)、[DevinoSolutions/anotifier](https://github.com/DevinoSolutions/anotifier-for-claude-codex-cursor)）；agent-watch-approve、ccpoke、Lucarne、forge-hub 以及一堆飞书/Telegram 一次性项目都在 2–4 个月内停更。**结论很硬：审批本身不是一个可持续的开源产品形态，而是用户期待被捆绑进来的一个功能。**

真正带"按风险自动放行"的只有四处。Pushary 是付费 SaaS（$9.99 / $19.99 / $59 每月，3 天试用，无免费层），卖的就是"one per-tool policy covering Claude Code, Codex, Cursor and Gemini CLI"、跨机器跨 agent 的 allow/ask/deny、不可篡改审计和 Pro 档的 "Policy Autopilot suggestions"（[pushary.com/pricing](https://pushary.com/pricing)、[pushary vs Remote Control](https://pushary.com/vs/claude-code-remote-control)）；Greenlight 是 iOS 封闭应用，免费加 $2.99 的 Autopilot，声称 "rules tune to each project over time"，Show HN 只拿到 1 分（[App Store](https://apps.apple.com/us/app/id6758998897)、[HN showcase](https://hnshowcase.com/post/47334316/greenlight-manage-your-ai-coding-agents-from-your-phone)）；agent-watch-approve 是正则危险清单，README 自己警告 "anything the pattern list misses will run without confirmation"，6 月后停更（[agent-watch-approve](https://github.com/ghy196830-del/agent-watch-approve)）；claude-threads 的 `auto` 只是复用 Claude 自己的分类器。其余全部二元：要么每条都转发，要么一个全局 yolo / Full access 开关。规则层因此是明确的变现点而非商品化能力，而开源里做出来的规则层都是单人正则项目，几个月就死。

用户对这些工具的抱怨落在四簇。安全簇：Happy #101 自 2025 年 9 月开着，原话 **"I'm not confident that I can get permission from work to run what's essentially a remote backdoor into my dev machine ... I just want to be able to use it from the kitchen"**，维护者的回答是自己起服务器，后续评论要 docker-compose（[slopus/happy #101](https://github.com/slopus/happy/issues/101)）；Telegram 路线的代价是 bot token 等于 root 凭据，"if someone gets your Telegram bot token, they can send commands to your running Claude Code session"（[MindStudio](https://www.mindstudio.ai/blog/claude-code-channels-vs-openclaw-mobile-agent-control)）。可靠性簇：Happy #302 "Codex gets stuck when requesting permissions" 13 条评论一片 "same"（[slopus/happy #302](https://github.com/slopus/happy/issues/302)）、Remodex #34 点"Approve"实际发出的是拒绝、cc-connect #1091 飞书消息"永久排队"、#1776 OpenCode 的目录授权被直接自动拒绝（[cc-connect #1776](https://github.com/chenhg5/cc-connect/issues/1776)）。部署簇：Happy #420 要分步 Docker 教程，claude-threads 要 Bun 加独立 bot 账号，ccpoke 要 tmux 加 Cloudflare tunnel。主机可用性簇：Mac 睡眠、Remote Control server mode 离线约 10 分钟后退出、Remodex 25 秒看门狗。**这四簇里最有辨识度的是可靠性：失败的通常不是通知送达，而是审批往返本身（挂起、卡死、误拒）**，而能把"答案一定落地，否则退回终端"做成可验证承诺的工具，就是在做别人没做成的事。Tailscale 已成为"不要中继"阵营的事实标准（CC Pocket、Remodex 均推荐），中国用户群（cc-connect 的基本盘）最在意的则是免公网 IP 与用户隔离。

## 安全放行的真相：确定性规则双向失效，用户要的是"按行为而非文本"的提示

三家 CLI 在 2026 年末收敛到同一个形状：一层确定性（allow / ask / deny 规则加 OS 沙箱）、一层概率性（分类器或 LLM 审阅）、一条硬底线。Claude Code 是唯一把底线写成文档且不可覆盖的：关键路径 `rm`/`rmdir` "which no allow rule or 'allow' hook approves"、受保护路径写入、显式 ask 规则，在 `bypassPermissions` 下依然生效（[Permission modes](https://code.claude.com/docs/en/permission-modes)）。厂商自己承认确定性匹配不是安全边界：Bash 规则 "isn't a security boundary around the program"，`Bash(rm *)` 不匹配 `/bin/rm` 或 `bash -c 'rm …'`（[Permissions](https://code.claude.com/docs/en/permissions)）；Codex 的拆分在遇到 "Redirection, substitutions, environment variables, wildcards, and control flow" 时整体放弃（[Codex rules](https://learn.chatgpt.com/docs/agent-configuration/rules)）。分类器的数字也给了边界：Anthropic 称 auto mode 分类器 "catches roughly 83%" 的过激行为、误拦约 0.4% 的良性命令，沙箱让提示减少 84%（[Anthropic, How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)）；独立压力测试报出 "81.0% end-to-end false negative rate on ambiguous authorization prompts"（[backslash.security 转述](https://www.backslash.security/blog/claude-code-auto-mode-catches-a-lot-but-not-everything)）；用户侧的误报 issue（#89922 "Blocked by classifier" 无具体原因、#70837 拦常规脚本、#71288 拦正常 PR 合并）持续出现（[claudeissues 89922](https://claudeissues.com/issue/89922-auto-mode-classifier-false-positives-on-codex-exec-and-cross-tool-state-files)）。Willison 的立场是分类器方向本身错了："guardrails catching 95% of attacks" 是 "a failing grade"（[The lethal trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)）。学术侧 CARE 用 bashlex AST 做静态分级，F1 85.64%、FPR 0.91%、延迟 2.32 ms，明确自称 "a complementary pre-execution defense rather than a replacement for sandboxing"（[CARE paper](https://arxiv.org/html/2607.21642v1)）。

从这些证据里能提炼出用户真正要而厂商都没给的三样东西。第一是**提示要键在"新行为"而非"新命令文本"上**："Continue? Y/N" 讨论串里 dns_snek 抱怨沙箱 agent 失败后 "ask you to allowlist the command as a whole, forever"，他想要的是 "every time a command tries to do something new" 才问（[HN 48308376](https://news.ycombinator.com/item?id=48308376)）。第二是**决定时选作用域**：Codex #22181 要的是 session / exact-args / workspace / duration 四选一（[openai/codex #22181](https://github.com/openai/codex/issues/22181)），而现在所有工具（包括手机端的 "Always approve"）存的都是程序前缀规则，同时太宽（Codex `curl`）又太窄（Claude 复合命令拆分）。第三是**跨 CLI 可移植的规则**：agentperms、gperm、ai-rulez 这些"一份 YAML 生成三家配置"的工具都存在且都承认转换有损，MCP 与内容范围规则不能往返（[paulochastinet/agentperms](https://github.com/paulochastinet/agentperms)、[igtm/global-permission](https://github.com/igtm/global-permission)）。事故模式也值得单独记：PocketOS 与 `terraform destroy` 删掉 1,943,200 行的案例，都不是 shell `rm -rf`，而是 agent 手里握着通往带外系统（云 API、Terraform、数据库）的活凭据（[Euronews](https://www.euronews.com/2026/04/28/an-ai-agent-deleted-a-companys-entire-database-in-9-seconds-then-wrote-an-apology)、[Medium 转述](https://medium.com/@chenyuan19920509/ten-ai-agents-destroyed-production-data-not-one-vendor-published-a-postmortem-8907211a68d2)）；shell 前缀白名单拦不住这些，按"目标不可逆性"定级的硬底线和凭据收窄才行。团队诉求（中央 deny-wins 策略、带 agent 归属的审计、破坏性动作的第二审批人）目前只有前两项被厂商和 GitHub 的 agent control plane 覆盖（[GitHub changelog](https://github.blog/changelog/2026-02-26-enterprise-ai-controls-agent-control-plane-now-generally-available/)），第二审批人只在开源治理项目和文章里出现，并附带 "blocks solo developers" 的警告（[DEV, two-person rule](https://dev.to/drkashy/a-two-person-rule-for-ai-coding-agents-9ld)）。

## Railse v0.2.0 覆盖了四个缺口中的三个半，短板集中在 Codex、Gemini 与"看不见数据"

逐条对照五个痛点，Railse 的位置如下。对第二痛点（谁在等我）与第四痛点（手机批/答），Railse 对 Claude Code 是全功能：`PermissionRequest` 可批可拒，`AskUserQuestion` 选择题可在手机作答（单选、多选、自填 ≤1000 字、交回终端），"等你回答"与"完成"进收件箱展示（[internal/adapter/claude.go](/Users/xufei/RailseWork/internal/adapter/claude.go)、[docs/web.md](/Users/xufei/RailseWork/docs/web.md)）。实测推送 1.4–2.5 秒到 iPhone（[design.md](/Users/xufei/RailseWork/docs/superpowers/specs/2026-10-21-railse-opc-design.md)）。对第三痛点（安全放行），Railse 是四家第三方之外少见的开源确定性规则层：七档风险（read → write_in_project → unknown → write_outside → network → outward → destructive），复合命令按 `&&`、`||`、`|`、`|&`、`;`、`&`、换行拆段取最高档，allow 须每段命中、deny 任一段命中，`sh -c` / `bash -lc` 内联串递归拆开，敏感路径与 `/dev/tcp` 抬级（[internal/policy/risk.go](/Users/xufei/RailseWork/internal/policy/risk.go)、[internal/policy/classify_shell.go](/Users/xufei/RailseWork/internal/policy/classify_shell.go)）。硬底线写在代码里：risk ≥ outward 的放行只能来自 `source: user` 规则，destructive 还必须显式写 `risk: destructive`，"记住"永远学不出这两档（[internal/policy/engine.go](/Users/xufei/RailseWork/internal/policy/engine.go)、[internal/policy/learn.go](/Users/xufei/RailseWork/internal/policy/learn.go)）。这正好对应上一节"按目标不可逆性定硬底线"的结论，也是 Railse 相对 Pushary（收费）和各种 yolo 开关最清楚的差异点。对官方留下的四个缺口，Railse 占了三个半：三 CLI 一个收件箱、自托管（本机 hub + Tailscale Funnel 一条命令，或 VPS 内置 ACME，或 Fly.io；"No cloud account"）、不依赖 claude.ai 账号因此天然服务被 Remote Control 排除的 API key / 网关用户，以及规则以 hub 为唯一真相整套下发到所有机器（[README.en.md](/Users/xufei/RailseWork/README.en.md)、[docs/hub.md](/Users/xufei/RailseWork/docs/hub.md)）。fail-open 原则 "A Railse failure never blocks an agent or approves anything" 直接命中第三方工具最常见的"审批往返挂起"失败簇（[README.en.md](/Users/xufei/RailseWork/README.en.md)）。

短板也同样清楚，而且几条比 README 写的更重。**Codex**：只在交互会话触发、`codex exec` 完全不介入，没有 question 事件，而 2026-10-21 的实验记录是 Codex 0.145.0 "代码模式下模型约 8 到 10 分钟主动放弃等待，长等待实际不可靠"（[hook-spike-findings.md](/Users/xufei/RailseWork/docs/superpowers/specs/2026-10-21-hook-spike-findings.md)）；对比 Claude 的 24 小时钩子超时，"去吃饭回来再批"这个卖点在 Codex 上的实际窗口只有十分钟，而仓库里没有对更新版本的复测。**Gemini**：钩子只能 deny 不能 allow，"Gemini 的请求永远不进 hub"（[docs/agent-local-loop.md](/Users/xufei/RailseWork/docs/agent-local-loop.md)），而上一节已说明 Gemini CLI 本身自 6 月 18 日起不再服务免费与 Pro/Ultra 个人用户；"Three CLIs, one inbox" 的措辞对 Gemini 用户实际兑现的是"规则层硬拒绝加完成提醒"，且目标产品正在萎缩。**"记住"的覆盖**：复合命令、含 `$()` / 子 shell / heredoc / 通配 / 重定向的命令、无项目根的命令全都 422，只能手写 YAML 导出再导入，网页没有编辑器（[docs/hub.md](/Users/xufei/RailseWork/docs/hub.md)、[docs/web.md](/Users/xufei/RailseWork/docs/web.md)）；这和 Claude Code #34106 用户痛骂的"allowlist 形同虚设"是同一个坑，只是 Railse 把它挪到了自己这边。**看不见数据**：设计验收标准是"使用一周后八成以上 `permission` 请求由规则自动决定"，但 hub 的 `requests` 表、`rules.hit_count`、`audit.jsonl` 都有原始数据而没有任何统计接口、页面或导出，设计文档说的审计导出端点在路由表里不存在（[internal/hub/api.go](/Users/xufei/RailseWork/internal/hub/api.go)、[internal/hub/store/schema.sql](/Users/xufei/RailseWork/internal/hub/store/schema.sql)）。**投递可靠性**：推送队列在内存里、hub 重启丢未发推送、满 256 条丢弃，iOS 上"应用划掉、锁屏、数小时后"三项真机结果仍写着 "hasn't been fully tested yet"（[docs/hub.md](/Users/xufei/RailseWork/docs/hub.md)、[README.en.md](/Users/xufei/RailseWork/README.en.md)）。**分级语料的一个洞**：`echo 'rm -rf ~' | sh` 在语料里是 `unknown` 而非 `destructive`，推断 `curl … | sh` 同样不会被标为最高档，而这恰是 Claude auto mode 与 Codex Auto-review 都默认拦截的模式（[shell_corpus.tsv](/Users/xufei/RailseWork/internal/policy/testdata/shell_corpus.tsv)）。还有一个仓库里没人写下来的风险：Claude Code 自 v2.1.283 起默认 auto mode，官方决策顺序是"规则 → 工作目录内只读/编辑自动放行 → 其余交分类器"，`PermissionRequest` 钩子在这条链上的位置文档没写，Railse 收到的 Claude 审批流量是否已经悄悄变少、哪些类型还会到手机，没有验证记录。

## 下几版：先验证，再算账，再把"记住"做对；五件事明确不做

排序原则是：先消除会让现有卖点失真的未知（成本最低、风险最高），再做能把"省掉多少次打扰"变成可见数字的事（营销与产品决策都靠它），然后才是扩展覆盖面。**第一位是验证 auto mode 默认下的钩子链路**：在 Claude Code ≥2.1.283 上实测 `PermissionRequest` 是否在分类器之前、之后还是被绕过触发，哪些请求（ask 规则、`AskUserQuestion`、关键路径 `rm`、受保护路径写入）仍到手机；结果决定 README 的措辞和后续优先级，成本一天以内。**第二位是统计页加审计导出**：对 `requests` 按 `kind='permission'` 与 `state IN ('auto_allowed','auto_denied','approved','denied','passthrough')` 聚合，给出"本周自动决定占比、人工批准最多的前十条命令、推送到决定的中位时延"，并补 `GET /api/audit/export`（JSONL/CSV）；这是零新依赖的纯读接口，顺便兑现设计里延后的"七天内同一前缀手动批准三次则建议建规则"，直接打第一痛点。**第三位是"记住"的作用域与精确模式**：在手机决定页加"只记这一条精确命令 / 这个项目 / 全局"三选，精确模式用 hub 已有的锚定 `command_regex: ^…$` 机制（现在只用于拒绝）生成放行规则，从而让复合命令、含重定向、`gh pr view`、`docker compose up` 这类目前 422 的日常命令可以一键记住，同时保持 outward / destructive 不可学的硬底线不变；这正是 Codex #22181 和 HN "Continue? Y/N" 讨论里用户点名要的原语，成本中等。**第四位是投递可靠性**：推送队列落 SQLite、hub 重启续发，完成 iOS 三项真机验证并把结果写进 README；若锁屏数小时后 Web Push 不可靠，再把 Bark 作为 iOS 备用渠道（设计文档已列为候选），不要上 Telegram——bot token 即 root 的安全簇已经被充分记录。**第五位是 `curl | sh` 与管道到 shell 的定级修正**：把 `| sh`、`| bash`、`bash -s`、`eval "$(curl …)"` 归到 destructive 或至少 outward，与两家厂商分类器默认行为对齐，成本半天。

覆盖面扩展放在这些之后，并且要带条件。**Antigravity CLI 适配**：先做一个两天的 spike 验证 `~/.gemini/config/hooks.json` 的 `PreToolUse` 是否如第三方所述 allow 不跳过确认；若是，则做与 Gemini 同构的 deny-only 适配并把 Gemini CLI 标为 legacy，`railse doctor` 据此提示；16% 的使用份额值得一个 deny-only 适配，但不值得为它做更多。**Codex 的等待窗口**：复测当前版本模型放弃等待的时长，在收件箱卡片上显示"对方最多再等约 N 分钟"，并把 `codex exec` 不介入写进对比表；不要试图用钩子"保活"，那是在对抗模型行为。**卸载命令与按机器暂停**：两件小事，都在用户问答里被点名，各半天。**Cursor CLI**：Stack Overflow 份额 25.5%，Pushary / Greenlight / anotifier 都已支持，但本次调研没有拿到 Cursor 钩子 API 的一手文档，只建议列入 v0.4 评估，不承诺。

五件事不该做，每件都有证据。**不做自研分类器或 LLM 判定**（设计里预留的 `judge` 动作继续搁置）：Claude auto mode 与 Codex Auto-review 都已免费内建，Anthropic 自报 0.4% 误报但 17% 漏报、独立测试 81% 漏报，用户对分类器的抱怨正在从"太多提示"转为"为什么拦我 / 为什么没拦住"；Railse 的可解释确定性规则加硬底线恰是对位优势，自研分类器等于放弃它去和免费品正面竞争。**不做终端复用 / PTY / 读屏**：herdr 47k star 已占满，设计文档也早写明"永远不做"。**不做聊天桥**（把 agent 搬进飞书/Telegram）：cc-connect 16k star 加 629 个 open issue 说明那是另一种产品和另一种维护负担。**不做团队角色与第二审批人**：68% 的开发者偏好单 agent，Railse 是一人公司产品，第二审批人被文献明确标注为会堵死独立开发者；只需保证审计可导出，让团队用户自己接 SIEM。**不做托管中继 / SaaS**：Happy #101 的 "remote backdoor" 顾虑和 Pushary 无 SOC 2 的短板都说明自托管是 Railse 最清楚的护城河，哪怕 Funnel 方案的代价（机器睡眠即离线、登录页暴露公网）也应该用文档如实承担，而不是用中继换便利。此外，**给 agent 回自由文本**（Codex / Gemini 的问题、"停下来等下一句"）在三家都没有钩子注入路径，Channels 又是只收白名单插件的 research preview，继续列为不做，直到 Channels GA 并开放第三方 permission relay。

## 结论

这轮调研改变了两个判断。其一，"手机批准"作为独立卖点的窗口正在关闭：三家官方都给了手机路径，Claude Code 更把 auto mode 设为默认，手机上要批的东西正在从"一切"收缩为"ask 规则、选择题、关键删除"这几类高权重事件。Railse 的长期价值因此不在"能在手机上点 Allow"，而在三件官方做不了或不愿做的事：一份可解释的确定性规则治三家 CLI、不经任何厂商中继、以及把"记住"做成带作用域的精确规则而不是又一个程序前缀白名单。其二，这个赛道的死亡原因不是功能少而是不可靠：第三方工具的 issue 里最密集的是审批往返挂起、误拒与推送丢失，而不是缺某个按钮。Railse 已有的 fail-open 是对的起点，下一步必须把它变成可度量、可导出、可在 README 里引用的数字——"上周 83% 的审批由规则自动决定，中位 6 秒到手机，0 次卡住"这一句话，比再支持一个 CLI 更能回答用户的真实问题。

Gemini → Antigravity 的替换还提示一个更一般的教训：适配层押注的是厂商的钩子语义，而厂商一年内会改名、改默认、换产品。Railse 应把"每个 CLI 能批 / 只能拒 / 只能提醒"的能力矩阵做成 `railse doctor` 的实时输出和 README 的首屏表格，让用户在装之前就知道自己那家 CLI 兑现的是哪一档承诺；这比任何营销措辞都更能守住信任。
